# Proof brief and provenance

## Minimal reusable brief

| Field | Decision |
| --- | --- |
| Audience / action | Who should understand this and what can they do next? |
| Positioning | What evidenced capability should this item demonstrate? |
| Source locators | Supplied files, public URLs, revision/access dates |
| Claim ledger | Final claim, literal quote, verification, attribution, scope, caveats |
| Public-use boundary | Public, anonymize, private, or unresolved for each fact/visual |
| Asset format | Card, short case PDF, architecture walkthrough, or existing work link |
| Structure | Context, role, decision, outcome/learning, proof, invitation |
| Delivery | Requested paths, editable source, exports, text equivalent, QA receipt |

A case PDF might need only a few pages; choose length from the argument, not a
fixed asset template. A card should communicate one supported point and lead to
inspectable evidence. Do not squeeze an entire CV onto a thumbnail.

## Evidence and project context

Read designated source facts, not just previous profile copy. A verified evidence
entry must agree with its current primary source, role, employer/project, dates,
units, and contribution scope. Unverified, cannot-confirm, or retracted entries
cannot support public claims. Ask neutrally about unresolved facts; never supply
a plausible metric for the candidate to adopt. Conflicting numbers stay out of
final copy until reconciled, while unaffected claims can proceed.

For a named job-intelligence project, resolve its current root and instructions.
Discover configured candidate sources and evidence-bank paths; inspect the live
quality contract and relevant memory. Candidate files remain immutable and the
evidence bank remains a derived index. Do not run application-preparation,
publication, database, status, or notification commands merely to build assets.
The profile-optimizer package is optional; this workflow does not require it.

Source excerpts may contain private employer/client facts. Verification establishes
support, not permission to redistribute. Anonymization must retain the supported
meaning; it cannot turn a private metric into an invented public approximation.
An inaccessible repository is not evidence of a non-existent project, but it also
cannot be advertised as a working public proof link. Use a permitted explanation
or another item. Never embed private excerpts or credentials into a public source
bundle, PDF attachment, image, URL, or export metadata.

## Acceptance receipt

Record what was actually checked:

- Each final factual assertion maps to verified, correctly attributed evidence.
- Each disclosed fact, screenshot, logo, and diagram is suitable for public use.
- All pages and cards were rendered and visually inspected at useful viewing sizes.
- PDF text extraction preserves the intended facts; PNGs have a text equivalent.
- Links resolve to the intended work and their visibility matches the audience.
- Exports and metadata contain no unintended private data.
- Upload compatibility is verified on a named current surface, or clearly pending.

Do not mark an unavailable check passed. Layout QA and exact quotation checks
do not establish semantic truth or permission. A plan/copy-only request needs no
rendering, but must not be reported as a produced asset kit.
