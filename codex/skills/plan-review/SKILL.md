# Plan Review

Critique an implementation plan before coding starts. The output is a read-only review that identifies blockers, significant risks, useful suggestions, and questions. Do not rewrite the plan or modify repository files.

## Review Depth

Choose the requested depth; default to `deep`:

- `quick`: check requirements coverage and blockers only.
- `deep`: validate all applicable criteria, repository assumptions, and similar implementations.
- `final`: assume the plan is mostly correct and try to break it with production edge cases, rollback gaps, and unhandled failure modes.

For `quick`, keep repository inspection bounded to explicitly referenced files plus requirements/instructions. For `deep` or `final`, read at most three comparable implementations unless a blocker requires one more targeted lookup.

## Load Context

1. Locate the plan from the supplied text, file, task description, or current conversation. If no plan can be identified, ask for it instead of reviewing a guessed outline.
2. Discover applicable project instructions across common layouts, including `CLAUDE.md`, `AGENTS.md`, `CODEX.md`, `.claude/rules/`, `.codex/rules/`, and repository-local instruction files.
3. Read the requirements source when present. Common candidates include `.claude/context/requirements.md`, `.codex/context/requirements.md`, `requirements.md`, a PRD, issue description, or explicit acceptance criteria in the request.
4. Read only the repository files needed to verify plan claims. Use read-only inspection and do not infer that a file, dependency, pattern, or invariant exists without evidence.

If multiple instruction or requirements sources conflict, report the conflict and identify which source appears authoritative based on repository conventions. Do not silently resolve it.

## Validate the Plan

Identify the goal, scope, steps, affected components, expected outcome, dependencies, and verification strategy. Then check:

- referenced files, symbols, commands, and directories exist
- proposed patterns match the current architecture and nearby implementations
- dependencies, imports, interfaces, and data flows are plausible
- relevant security and privacy boundaries are addressed
- destructive or irreversible operations have rollback or recovery steps
- tests cover the changed behavior and likely failure modes
- steps are ordered correctly and can be parallelized where that is safe
- the plan avoids unrequested scope expansion

Review two or three similar implementations when the plan relies on a pattern that can be compared locally. Cite the comparison as evidence or report that no comparable implementation was found.

## Requirements Alignment

When explicit requirements exist, apply these rules:

- `R1`: every acceptance criterion maps to a plan step; list missing or partial coverage.
- `R2`: no plan step adds functionality beyond the requested scope without justification.
- `R3`: ambiguities, contradictions, and missing acceptance details appear in `QUESTIONS`.

Do not manufacture requirements. If no requirements source exists, state that traceability could not be verified.

## Review Criteria

Apply the criteria appropriate to the plan and review depth.

### Correctness

- `X1`: incorrect assumptions about existing code, data, or behavior
- `X2`: missing steps that could make implementation fail
- `X3`: security vulnerabilities such as injection, authorization bypass, or data exposure
- `X4`: breaking public API or data changes without migration or compatibility strategy

### Architecture

- `A1`: plan violates established layering or project conventions
- `A2`: plan violates a documented invariant or instruction
- `A3`: proposed patterns do not match comparable implementations

### Completeness

- `C1`: likely error and failure modes lack handling
- `C2`: destructive changes lack rollback, migration safety, or recovery
- `C3`: important edge cases are missing
- `C4`: tests or verification do not cover the changed behavior

### Efficiency and Scope

- `E1`: safe parallel work is unnecessarily serialized
- `E2`: existing code or infrastructure is ignored, causing avoidable duplication
- `E3`: the plan expands beyond the stated goal without evidence or approval

Only report actual violations. Avoid style preferences, speculative criticism, and suggestions that do not improve correctness, safety, completeness, or maintainability.

## Evidence Standard

Every finding must include:

- rule ID when applicable
- severity: `critical`, `warning`, or `nit`
- location: plan step, requirement, or `file:line`
- explanation of the concrete risk
- a specific fix or question

Use `critical` for a blocker that could cause incorrect, unsafe, or unrecoverable implementation. Use `warning` for a material risk that should be addressed. Use `nit` only for a small but evidence-backed issue that is not blocking.

## Do Not

- Do not edit, rewrite, or reorder the plan.
- Do not modify repository files, checkout branches, install dependencies, or run state-changing commands.
- Do not report a violation without evidence or a clearly identified missing plan step.
- Do not duplicate the repository's code-review workflow; use `code-review` after implementation when the request is about a code diff.
