# Audit Memory

Scan agent memory files and report health issues. This skill is read-only: it reports findings but does not modify files, refresh sources, update indexes, stage changes, or run state-changing commands.

This is the verification member of the memory family:

- `create-memory` bootstraps a durable baseline.
- `ingest-memory` imports external or supplied knowledge.
- `update-memory` maintains knowledge learned during ongoing work.
- `audit-memory` checks the result for quality, drift, and broken relationships.

Keep the workflows separate. The family shares memory-root discovery, frontmatter, provenance, index, and cross-reference conventions.

Use this skill when the user asks to:

- audit memory health
- find stale memory files
- check broken memory cross-references
- review memory index consistency
- inspect source freshness for imported memories
- check whether memory directories are approaching size limits
- run an equivalent of a memory audit command from another agent environment

## Scope Discovery

If the user supplies a memory root, project root, or file list, use that as the primary scope.

When no scope is supplied, look for common memory layouts that exist on the machine:

- Claude-style global memories: `~/.claude/memory/*.md`
- Claude-style project memories: `~/.claude/projects/*/memory/*.md`
- Repository-local memories: `.claude/memory/*.md`, `.codex/memory/*.md`, `memory/*.md`, `memories/*.md`
- Project indexes named `MEMORY.md`

Do not assume every repository uses these paths. Treat them as discovery defaults, not universal requirements.

Build a registry for each discovered memory file:

```text
{path, filename, name, description, type, related[], last_updated, source?}
```

Read enough frontmatter or leading content to extract metadata. If a file has no parseable metadata, still include it in index, capacity, and reference checks.

### Family Convention Check

For files that use the family frontmatter convention, verify that:

- `name`, `description`, `type`, `related`, and `last_updated` are present when applicable
- `type` is `project`, `feedback`, or `reference`
- source-backed files preserve a `source` or equivalent provenance field
- related entries use stable local filenames or clearly identified external references

Report missing or invalid fields as warnings when they reduce maintainability, and as info when the host memory system documents a different valid schema. Do not rewrite platform-specific metadata during an audit.

## Checks

### 1. Stale Files

For each file with a `last_updated` date older than 30 days from today:

- If the file belongs to a project memory directory and the related project repository can be identified, inspect recent git activity with a read-only command such as `git -C <project-root> log --since="30 days ago" --oneline -1`.
- If there is recent project activity but the memory is stale, flag a warning.
- If the project appears dormant, treat staleness as informational or skip it unless the user asked for strict stale-memory reporting.
- If no project repository can be identified, report stale dates without inventing activity context.

### 2. Broken Cross-References

For each file with a `related:` array or equivalent cross-reference list:

- Verify each referenced filename exists in the same memory directory unless the reference clearly includes another path.
- Flag missing local references as critical.
- Treat external or cross-repository references as informational unless local policy says they must resolve.

### 3. Stale External Sources

For each file with source metadata, such as `source.type`, `source.ingested`, `source.url`, or equivalent fields:

- Check whether the source ingestion or refresh date is older than 30 days.
- Flag stale imported sources as warnings.
- Keep source-specific wording generic unless the source type is explicit. For example, say "external source" by default and "Confluence source" only when `source.type: confluence`.
- Do not refresh sources. Report the stale source and, if local docs define a refresh command, mention it as context rather than running it.

### 4. Vague Descriptions

For each file, check the `description` field:

- If it is fewer than 30 characters, flag a warning.
- If it is generic and lacks a specific subject, flag info. Generic terms include "info", "data", "reference", "overview", and similar labels when they appear without concrete domain context.

### 5. Index Consistency

For each memory directory with a `MEMORY.md` index:

- Parse local Markdown links, for example links whose target looks like `filename.md`.
- Dead links: flag links to missing local files as critical.
- Orphan files: flag `.md` files in the directory, excluding `MEMORY.md`, that are not listed in the index as warnings.

### 6. Bidirectional Cross-Reference Check

For every file A that lists file B in `related:`:

- Read file B's metadata when B exists.
- Check whether B also references A.
- If not, flag info: "A references B but B does not reference A."

### 7. Capacity Check

Count `.md` files, excluding `MEMORY.md`, in each memory directory:

- If count is above 75 percent of a known local hard limit, flag a warning.
- If count is above 95 percent of a known local hard limit, flag critical.
- If no local limit is documented, use the source workflow's `200` file limit as a compatibility default and state that assumption.

Also check `MEMORY.md` line count:

- If a local line limit exists, apply the same 75 percent and 95 percent thresholds.
- If no local limit is documented, use the source workflow's `80` line limit as a compatibility default and flag files above 70 lines as info.

## Report Format

Output a structured report:

```text
Memory Audit Report
===================

Scanned: <N> global files, <N> project files across <N> projects

## Critical Issues (<count>)
- [BROKEN REF] <source_file> references <missing_file>
- [DEAD LINK] <MEMORY.md path> links to non-existent <filename>

## Warnings (<count>)
- [STALE] <filename> - last_updated: <date>, repo last commit: <date or unknown>
- [STALE SOURCE] <filename> - external source ingested <date> (>30 days)
- [VAGUE] <filename> - description: "<text>" (<N> chars)
- [ORPHAN] <filename> not listed in <MEMORY.md path>
- [CAPACITY] <directory>: <N>/<limit> files

## Info (<count>)
- [ONE-WAY REF] <A> references <B> but not vice versa
- [GENERIC DESC] <filename> - description lacks specifics
- [INDEX SIZE] <MEMORY.md path>: <N>/<limit> lines

## Summary
<total> issues: <critical> critical, <warnings> warnings, <info> info
```

If zero issues are found, output:

```text
Memory Audit Report: All clear.
Scanned: <N> global files, <N> project files across <N> projects.
No issues found.
```

## Do Not

- Do not edit memory files.
- Do not create, rewrite, or sort indexes.
- Do not refresh external sources.
- Do not stage, commit, reset, checkout, or clean files.
- Do not assume Claude paths are the only valid memory layout.
- Do not treat dormant project memories as urgent stale findings without evidence of recent project activity.
