# Wrap Agent Skill

Create or update the canonical skill under `agent-plugins/skills/<skill-name>/`, then generate the Claude and Codex distribution copies.

The canonical `agent-plugins` skill owns the real instructions and bundled resources. The `claude/skills` and `codex/skills` trees are generated distribution copies:

```text
agent-plugins/skills/<skill-name>/  # edit here
claude/skills/<skill-name>/         # generated
codex/skills/<skill-name>/          # generated
```

## Workflow

1. Identify the source:
   - Existing canonical skill: `agent-plugins/skills/<skill-name>/SKILL.md`.
   - Generated local copy: `claude/skills/<skill-name>/SKILL.md` or `codex/skills/<skill-name>/SKILL.md`.
   - External platform source: `.claude/skills/<skill-name>/SKILL.md`, `.codex/skills/<skill-name>/SKILL.md`, or another supplied directory/file.
2. Read the source `SKILL.md` frontmatter, body, and referenced local resources before writing anything.
3. Decide whether the source is a real reusable skill. If it is not, stop and explain why instead of adding noise to the plugin.
4. Present the mandatory pre-add review and wait for explicit user approval before creating or editing any skill files.
5. After approval, create or update `agent-plugins/skills/<skill-name>/` as the universal canonical version.
6. Run `python scripts/generate_skill_wrappers.py <skill-name>` from the repository root.
7. Re-read the canonical and generated `SKILL.md` files, then verify:
   - the canonical directory name and frontmatter `name` match
   - the canonical `description` is platform-neutral and routing-friendly
   - Claude/Codex-specific implementation details have been generalized or fenced as platform-specific notes
   - bundled resources needed by the skill were copied into the canonical directory
   - generated copies contain the generated-file marker
8. Run `python scripts/generate_skill_wrappers.py --check --clean --strict-links` unless the user asked for a narrow partial edit.
9. After validation passes, summarize the changed files and ask whether the user wants to push/publish the changes. Do not commit, push, release, or publish unless the user explicitly approves that follow-up action.

If a target path is blocked by permissions or ACLs, report the blocked file and provide the exact wrapper content that should be written.

## Mandatory Pre-Add Review

Before adding, importing, or universalizing any new skill, stop after reading the source and give the user a short decision report. Do not create `agent-plugins/skills/<skill-name>/`, do not copy resources, and do not run the generator until the user explicitly approves.

The report must include:

- Score: rate the candidate from `0` to `100` for usefulness, reusability, clarity, portability, and maintenance risk.
- Pros: list the strongest reasons to add it.
- Cons: list the main risks, gaps, or repo-specific assumptions.
- Advice: say `ADD`, `ADD AFTER IMPROVEMENTS`, or `DO NOT ADD`, with one sentence explaining why.
- Improvement plan: explain whether it can be improved before import and exactly how.
- Approval question: ask the user whether to add it, improve then add it, or skip it.

Only proceed when the user clearly confirms approval, such as "add it", "yes add", or "improve then add". If the user asks to skip, stop without changing files. If the user approves improvements first, make only the approved improvements while creating the canonical skill.

## Post-Add Push Prompt

After adding or updating a skill and passing validation, ask the user whether to push/publish the changes.

Include:

- the canonical skill path
- generated Claude and Codex paths

Ask a direct question such as: "Do you want me to commit and push these changes now?" If the user says yes, follow the repository's normal git/publish workflow. If the user says no or does not answer, leave the changes local.

## Real Skill Detection

When a source comes from `.claude`, `.codex`, `claude/skills`, `codex/skills`, or a pasted platform-specific folder, do not assume it belongs in this plugin. First classify it.

A real reusable skill should have most of these traits:

- A clear capability that can be reused across projects or conversations.
- A `SKILL.md` or equivalent instruction file with concrete workflow steps.
- Routing frontmatter or enough title/body context to derive `name` and `description`.
- Boundaries: when to use it, when not to use it, expected inputs, and expected outputs.
- Enough procedural detail that another agent could execute it without hidden chat context.
- Optional resources such as `references/`, `scripts/`, `assets/`, examples, templates, or policies that support the workflow.

Reject or ask for clarification when the source is only:

- A project memory file such as `CLAUDE.md`, `AGENTS.md`, or global style preferences.
- A one-off prompt, chat transcript, scratch note, task plan, or personal reminder.
- A thin command alias with no reusable method behind it.
- A tool configuration, MCP manifest, plugin manifest, or settings file without skill instructions.
- Instructions that depend on private local state, absolute paths, credentials, or a single project in a way that cannot be generalized.

If the source is borderline, preserve it only after extracting a reusable workflow and clearly naming the assumptions in the final response.

## Universalization Rules

When importing a real skill from `.claude`, `.codex`, or another platform-specific source, tune it into a universal canonical skill before generating platform copies:

- Replace platform-only tool names with capability descriptions when the exact tool is not portable. Example: use "inspect repository files" instead of assuming one runtime's `Read` tool.
- Keep platform-specific tool allowlists only in frontmatter when both Claude and Codex can tolerate them; otherwise move platform-only guidance into a short compatibility note.
- Convert absolute paths, usernames, machine paths, and one-project references into arguments, placeholders, or repository-relative paths.
- Keep the skill's reusable method, examples, constraints, and quality bar; remove activation text that only makes sense in the original assistant.
- Rename the skill using kebab-case and make the `description` describe when an agent should use it, not where it came from.
- Copy only local resources that the universal skill actually needs. Do not copy caches, generated outputs, credentials, logs, or unrelated project files.
- If the source skill includes scripts, verify they are portable or document their runtime requirements.
- Prefer explicit "Do Not" constraints over hidden assumptions from the source platform.

## Frontmatter Rules

Start from the source description, then adapt for universal routing:

```yaml
---
name: <skill-name>
description: <Action>. Use when the user asks to <specific triggers>. <Important constraints or output expectations>.
metadata:
  trigger: <short trigger summary, if useful>
user-invocable: true
allowed-tools: <minimal compatible tool list, only if useful>
argument-hint: "<expected user argument shape>"
---
```

Write the description for agent routing. Include:

- what the skill does
- when the agent should use it
- common user phrasing that should trigger it
- important constraints, such as read-only behavior or required verification

- Keep useful `metadata` from the source, such as `trigger`, `author`, or short UI-facing context.
- Keep `user-invocable: true` when the skill should be directly callable.
- Set `allowed-tools` to the smallest useful set for the canonical workflow.
- Add `argument-hint` when the skill accepts files, folders, PR numbers, text scopes, or mode flags.
- Keep source-specific fields such as `effort` only when they are meaningful for both generated distributions.

Avoid vague descriptions like "helps with skills." The description is the routing surface.

## Tool Selection For Wrapper Allowlists

When a wrapper includes `allowed-tools`, choose them from the actual canonical workflow:

- Text-only editing or review: `Read, Grep, Glob`
- File creation or updates: `Read, Grep, Glob, Write, Edit, MultiEdit`
- Git diff or repository inspection: add `Bash(git diff:*), Bash(git status:*), Bash(git log:*), Bash(git show:*)`
- GitHub PR diff inspection: add `Bash(gh pr diff:*), Bash(gh pr view:*)`
- Avoid broad `Bash` unless the skill truly needs arbitrary shell commands.

When unsure, choose the narrowest set and mention the assumption in the final response.

## Do Not

- Do not edit generated files under `claude/skills/` or `codex/skills/` as the source of truth.
- Do not create extra README, changelog, or installation docs.
- Do not import a `.claude` or `.codex` file just because it exists; prove it is a reusable skill first.
- Do not preserve platform-specific wording when a platform-neutral instruction would work.
- Do not overwrite a handcrafted target without reading it first.
- Do not normalize unrelated canonical skills unless the user explicitly asks.
